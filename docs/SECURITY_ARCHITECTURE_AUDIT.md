# Аудит архитектуры безопасности — Sheber ERP

Чек-лист архитектурного security-аудита. Проходим по этапам, каждый этап — отдельный заход с результатом на проверку перед следующим.

Состав системы: Django 4.2 + DRF + PostgreSQL, Next.js фронтенд, React Native/Expo мобилка, деплой Railway (Gunicorn + WhiteNoise).

## Этапы (порядок проверки)

| Этап | Задачи | Почему в этом порядке |
|------|--------|------------------------|
| **0** | A1 — Scope и цели | Ручная задача пользователя: что входит в аудит, какие окружения, что критично для бизнеса. Без этого остальные этапы не на чем основывать. |
| **1** | B1 — Архитектура и trust boundaries | Карта системы (сервисы, точки входа, границы доверия) — на неё опираются все последующие этапы. |
| **2** | B2 — Threat modeling (STRIDE) | Требует готовой карты из этапа 1. Даёт список угроз, к которым привязываются остальные разделы. |
| **3** | C1 — IAM (identity & access) | Роли/права — одна из главных площадок угроз (elevation of privilege из STRIDE), логично сразу после threat model. |
| **4** | D1 — Сеть и сегментация | Инфраструктурный слой, независим от IAM, но опирается на карту из этапа 1. |
| **5** | E1 — Данные и шифрование | Что храним и как защищаем — соприкасается и с IAM (кто видит), и с сетью (как передаём). |
| **6** | F1 — Управление секретами | Логически примыкает к данным/шифрованию (ключи — тоже чувствительные данные). |
| **7** | G1 — Логирование, мониторинг, аудит | Проверяет, что PII/секреты не утекают в логи (зависит от результатов E1/F1) + видимость инцидентов. |
| **8** | H1 — Надёжность, бэкапы, инциденты | Отдельный пласт (эксплуатационная устойчивость), не зависит от предыдущих технически, но логично идёт после данных/логов. |
| **9** | I1 — Secure SDLC и деплой | Как код доезжает до прода — замыкает картину перед итоговым отчётом. |
| **10** | J1 — Итоговый консолидированный отчёт | Требует результатов всех предыдущих этапов. |

Этапы 3–9 не имеют жёстких технических зависимостей друг от друга (после этапов 0–2) — можно менять порядок, если что-то важнее прямо сейчас. Предложенный порядок — по естественному тяготению тем друг к другу.

## Как будем работать

- Один этап за раз. Результат каждого этапа — отдельный раздел/файл (например `docs/security-audit/B1-architecture.md`), не смешиваем с этим чек-листом.
- После каждого этапа отмечаю ☐ → ☑ в этой таблице и коммичу вместе с результатом.
- Прежде чем закрывать угрозу как решённую — грепаю код/конфиг, а не доверяю только описанию (в проекте уже был прецедент, когда декларативный документ расходился с реальным состоянием — см. `CLAUDE.md`).
