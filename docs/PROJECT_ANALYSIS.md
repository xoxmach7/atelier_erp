# Полный анализ проекта Atelier ERP (Sheber ERP)

Дата: 2026-06-04. Анализ как продукта для реального ателье (офис + склад + цех + монтаж).
Состояние ветки: `fix/p0-access-security`, P0 закоммичен (`24eeeab`, `1f3b31a`).

Это более глубокий взгляд, чем первичный аудит: архитектура, доменная модель, сервисный слой, API, клиенты, тесты, техдолг и дорожная карта. Первичные находки по безопасности доступа уже закрыты (см. `P0_CHANGES.md`) и здесь не повторяются как «критические» — они отмечены как сделанные.

## 1. Резюме

Проект сильно выше уровня типичного «pet-project»: продуманная слоистая архитектура, доменная модель под масштаб, шина событий, сервисный слой, отдельные клиенты (web + mobile), ~170 тестов. Это серьёзный задел.

Главный риск теперь — **не качество, а объём и незавершённость**: ~55 000 строк кода, из которых заметная часть либо дублируется (два инвентарных сервиса, два набора API), либо не активирована (events-шина и Celery-интеграция написаны, но Celery в боевых настройках не подключён). Для пилота это означает: система делает много, но не вся заявленная функциональность реально работает в текущей сборке, и сопровождать такой объём силами небольшой команды тяжело.

Вердикт готовности к пилоту: **близко, но не сегодня.** После P0 (доступ/безопасность закрыты) до пилота осталось P1 — данные (PostgreSQL, нумерация заказов, отзыв токенов) и приведение тестов/контракта клиентов в порядок. Реалистично 1–1.5 недели целенаправленной работы.

## 3. Архитектура

### Backend
Слоистая и дисциплинированная: модели → сервисы (`services/`) → API (DRF ViewSets/APIView). Бизнес-логика и переходы состояний вынесены в сервисы и `constants.py` (FSM-правила, гайды по статусам, коэффициенты). Это правильная и редкая для таких проектов зрелость — логика не размазана по вьюхам.

Дополнительно есть:
- **Шина событий** (`events/bus.py`, `audit.py`, `registry.py`, `definitions.py`) — событийная модель с аудитом.
- **Unit of Work** (`services/unit_of_work.py`) — транзакционные границы.
- **Планировщик и генератор задач** (`scheduler.py` 1402 стр., `task_generator.py` 1110 стр.).

⚠️ Существенно: вся эта событийно-планировочная инфраструктура **не подключена в боевых настройках**. В реальном `settings.py` нет конфигурации Celery (она только в `settings_example.py`), нет celery-app и `INSTALLED_APPS` без celery. То есть ~2.8k строк events + 1.4k scheduler + 1.1k task_generator — это потенциал, который сейчас либо не исполняется, либо исполняется синхронно/частично. Нужно осознанно решить: активировать (Celery + Redis + beat) или вынести из MVP, чтобы не тащить мёртвый вес.

### Frontend
Современный стек: Next.js 16, React 19, TanStack Query, shadcn/ui, Tailwind. 32 страницы, отдельный HTTP-слой (`services/http/*`), хуки (`useOrders`, `useQuotes`, `useWorkQueues`), ролевые рабочие пространства. Структура аккуратная.

### Mobile
Expo 54 / React Native 0.81, expo-router, 18 экранов, отдельный API-слой и `AuthContext` (JWT через `/api/auth/token/` + `/api/me/`). Реальный логин работает; есть демо-данные (`demoOrders`, `demoWork`) для офлайн-демо.

## 4. Доменная модель — сильная сторона

Сущности покрывают весь процесс ателье: `Customer`, `Fabric` + `FabricReservation`, `Cornice`, `Service`, `Order` + `OrderItem`, `Measurement`, `Quote` + `QuoteItem`, `OrderMaterial`, `ProductionAssignment` + `ProductionLog`, `SeamstressPayment`, `Payment`, `PhotoReport`, `OrderCompletionAct` (АВР), `Task` + история, `OrderStatusHistory`, `ActivityLog`.

Что сделано правильно:
- **Статусная цепочка** в `constants.py` (`new → in_work → in_production → ready → on_installation → waiting_final_payment → completed` + `cancelled`) совпадает с бизнес-правилами (`BUSINESS RULES.md`).
- **Операционные слои отделены от статуса**: `MaterialReadiness`, `ProductionStage`, `HandoverStage` — отдельные измерения, а не подмена главного статуса. Это точное попадание в бизнес-логику.
- UUID-ключи, индексы, check-constraints, `created_by/updated_by`, заявка на 100k+ заказов.
- Артефакты завершения как сущности (`PhotoReport`, `OrderCompletionAct`).

Слабое место — **легаси в FSM**: помимо MVP-статусов в правилах переходов остались `draft, measurement, design, quoted, approved, prepayment_received, fabric_reserved, production, installation`. Это и есть причина, по которой устаревшие lifecycle-тесты падают (ждут `draft`, код отдаёт `new`). Нужно вычистить.

## 5. Сервисный слой — дублирование и незавершённость

14 модулей, ~8 400 строк. Сильный слой, но с двумя проблемами:

1. **Дублирование инвентаря**: `inventory_service.py` (554) и `inventory_v2.py` (1143) оба существуют и оба экспортируются из `services/__init__.py`. Почти наверняка v1 — легаси. Нужно определить единственный источник истины и удалить второй, иначе расхождение логики резервирования ткани — вопрос времени.
2. **Возможное пересечение** `order_service.py` (1295) и `order_execution_service.py` (1171) — два больших сервиса вокруг заказа; стоит проверить границы ответственности, нет ли дублей переходов.

Положительное: исключения вынесены (`exceptions.py`), есть UoW, платежи и производство — отдельными сервисами.

## 6. API

Двойной набор:
- **Legacy** `/api/` (`api/views.py`) — создание заказа заблокировано (405), но остальные ViewSet'ы активны.
- **v1** `/api/v1/` (service-layer) — основной: `orders, tasks, inventory, quotes` + 7 рабочих очередей (`work/designer|quotes|warehouse|production|installation|owner|finance`) + `dashboard`.

Проблема: два параллельных API увеличивают площадь поддержки и риск, что правку (например, ролевой срез) сделают в одном, но забудут в другом. В P0 я закрыл срез в обоих, но стратегически legacy надо депрекировать.

Аутентификация — JWT (SimpleJWT), `IsAuthenticated` по умолчанию. После P0: ролевые срезы, скрытие финполей, гарды очередей. Остаётся (P1): отзыв токенов (blacklist), throttling логина.

## 8. Тесты

~170 тест-функций, 14 файлов. Хорошее покрытие: модели (18), сервисы (42), API (23), интеграционные сценарии (11), КП-расчёты (7), фотоотчёт (9), АВР (16), ролевой доступ (8, добавлено в P0).

Проблемы:
- **Устаревшие lifecycle-тесты** (`test_order_lifecycle_api`, `test_order_lifecycle_v1_api`) ждут легаси-статусы (`draft`, `quoted→approved`) и поведение, которого нет в MVP-модели → 11 падений по статусам/FSM и 401-vs-403. Это дрейф тестов от кода, не баги продукта.
- **2 пред-существующих error'а**: `test_order_quote_linkage.py` (в корне) — debug-скрипт с `raise Exception("Rollback")`, ломает discovery; `test_reserve_materials_via_api` — передаёт в `OrderItem` несуществующие поля.
- Нет тестов на отзыв токенов, throttling, конкурентную нумерацию заказов — добавить вместе с P1.

## 9. Техдолг и риски (после P0)

🔴 **Данные под многопользовательской работой:**
- SQLite по умолчанию — блокировки записи при одновременной работе офиса/склада/цеха. Нужен PostgreSQL.
- Нумерация заказов через `count()+1` — гонка, дубликаты номеров под нагрузкой (есть `ORDER_NUMBER_LOCK` в константах, но не используется).

🟠 **Аутентификация:** токены нельзя отозвать (нет blacklist), нет throttling логина (брутфорс).

🟠 **Неактивированная/дублирующая инфраструктура:** events+Celery не подключены; два инвентарных сервиса; двойной API. Либо активировать осознанно, либо урезать — иначе растёт стоимость поддержки.

🟡 **Чистота:** легаси-статусы в FSM; устаревшие тесты; демо-страницы и демо-данные вперемешку с боевым кодом; мёртвый `mobile/api/auth.ts`.

🟢 **Хорошо:** доменная модель, сервисный слой, разделение операционных слоёв, ролевой доступ (после P0), широкое покрытие тестами, современные стеки клиентов.

## 11. Дорожная карта

**P1 — данные и надёжность (до пилота), ~3–4 дня**
1. PostgreSQL вместо SQLite; убрать `db.sqlite3` из репо.
2. Атомарная нумерация заказов (sequence / `select_for_update`).
3. JWT blacklist + ротация + серверный logout; throttling логина.
4. Привести устаревшие lifecycle-тесты к MVP-статусам; починить 2 error'а; добиться зелёного прогона.

**P2 — консолидация архитектуры, ~3–5 дней**
5. Решить судьбу events/Celery: активировать (Redis+beat, оповещения о сроках и закупках) или вынести из MVP.
6. Удалить дубль инвентаря (`inventory_service` vs `inventory_v2`); проверить границы `order_service`/`order_execution_service`.
7. Депрекировать legacy `/api/`, оставить v1.
8. Явные доменные действия «принят» и «передать в цех» с гардами (КП согласовано + материалы).

**P3 — продукт и чистота, ~2–3 дня**
9. Mobile: удалить мёртвый `auth.ts`, демо-данные за флаг, default-deny роли.
10. Frontend: отделить демо-страницы (`mvp-preview`, `product-demo`, `workflow-map`) от боевого UI.
11. Вычистить легаси-статусы FSM.
12. Тесты на токены/throttling/нумерацию; замер покрытия.

## 12. Критерии готовности к пилоту (go / no-go)

Пускать реальное ателье можно, когда:
- [x] Каждый сотрудник видит только свой срез; финансы — только владельцу/дизайнеру (P0 ✅).
- [x] Конфигурация безопасна для прода (P0 ✅).
- [ ] БД — PostgreSQL, нумерация заказов без гонок (P1).
- [ ] Токены отзываются, логин под throttling (P1).
- [ ] Тесты зелёные (P1).
- [ ] Понятно, что из events/инвентаря/API реально работает, а что — мёртвый вес (P2).

Первые пять пунктов — обязательны до первого живого заказа. Шестой можно закрывать параллельно с пилотом, но не позже.

## Итог
Фундамент сильный, и P0 снял главные блокеры безопасности. Оставшийся путь до пилота — это в основном надёжность данных (P1) и наведение порядка в том, что уже написано (P2), а не написание нового. Самый недооценённый риск — объём незавершённой/дублирующей инфраструктуры: её нужно либо включить, либо убрать, иначе она будет тихо съедать время на сопровождение. Конкретный следующий шаг утром — P1, пункт 1 (PostgreSQL) и пункт 4 (зелёные тесты).
