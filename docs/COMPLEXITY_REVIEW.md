# Аудит сложности / over-engineering

Дата: 2026-06-04. Критерий оценки — философия из `PROJECT_CONTEXT.md`:
**«Простота важнее количества функций. Любая функция должна отвечать: какую конкретную работу сотруднику она помогает выполнить?»**

Короткий вердикт: **да, переусложнили — но не везде, а в инфраструктуре.** Примерно четверть backend-кода (вне тестов) — это «движки», которые сейчас ничего не делают в рантайме. При этом то, что заявлено как ядро продукта (экран Work = только свои задачи по ролям), наоборот недостроено. То есть сложность вложена не туда.

---

## 🔴 Главное: мёртвая инфраструктура (~5.3k строк работают вхолостую)

### 1. Шина событий `events/` (~2 800 строк) — публикует в пустоту
`events/bus.py, audit.py, registry.py, definitions.py, celery_integration.py`. Сервисы честно публикуют доменные события (`UnitOfWork.publish(...)`), **но ни одного подписчика во всём проекте нет** (поиск `.subscribe(` / `register_handler` вне `events/` — пусто). Плюс Celery нигде не сконфигурирован: нет `atelier_erp/celery.py`, нет `CELERY_*` в боевом `settings.py`. Итог: события улетают в никуда, асинхронность не работает.
- **Почему это переусложнение:** 2.8k строк абстракций (event bus, registry, celery-интеграция) дают ноль функциональности сейчас. Аудит, ради которого это вроде задумано, и так делается проще — через `signals.py` (он работает и пишет `ActivityLog`).
- **Что делать для MVP:** убрать публикацию событий из горячего пути (или оставить тонкий no-op), а `events/` вынести из MVP (в отдельную ветку/папку `future/`). Аудит оставить на сигналах.

### 2. `scheduler.py` (1 402) + `task_generator.py` (1 110) — не вызываются нигде
~2 500 строк. Поиск вызовов `TaskGenerator(`, `scheduler.` из API и сервисов (вне самих этих файлов и тестов) — **пусто**. Это сложный движок генерации задач (DAG, шаблоны продуктов) и планировщик, которые в работающем приложении не дёргаются.
- **Почему переусложнение:** огромный, умный, но «спящий» код. Его надо понимать, тестировать, тащить — а пользы в рантайке нет.
- **Что делать:** для MVP вынести из основного пакета. Когда реально понадобится автогенерация задач — вернуть точечно.

> Итого по «движкам»: ~5.3k строк из ~20k backend-кода (≈25%) — это сложность без текущей отдачи. Это и есть главный ответ на «не переусложнили ли мы».

## 🟠 Дубли и двойные контуры

### 3. Два инвентарных сервиса
`inventory_service.py` (554) и `inventory_v2.py` (1143) — оба экспортируются из `services/__init__.py`. Логика резервирования ткани в двух местах → риск разъезда.
- **Что делать:** оставить один (вероятно v2), удалить второй, поправить импорты.

### 4. Два набора API (`/api/` + `/api/v1/`)
Legacy `api/views.py` и `api/v1/views.py`. Поддерживать надо оба, и правки (как ролевой срез в P0) приходится дублировать.
- **Что делать:** оставить только v1, legacy заморозить/удалить.

### 5. Два больших сервиса вокруг заказа
`order_service.py` (1295) и `order_execution_service.py` (1171). Здесь не чистый дубль — `order_execution_service` реально используется (даёт доступные действия/предупреждения/блокеры для UI). Но границы размыты, оба огромные.
- **Что делать:** не срочно. Зафиксировать, кто за что отвечает; при рефакторинге не плодить переходы в двух местах.

## 🟠 Концептуальный разрыв с твоей же философией (важнее всего для продукта)

`PROJECT_CONTEXT` прямо говорит: мобайл = **задачи по ролям**, экран **Work** показывает «только то, что должен сделать сотрудник», Warehouse **не должен видеть весь заказ — только задачи по материалам**.

А по факту: backend и клиенты — **заказ-центричные**. Роли получают **срез списка заказов по статусу** (это мы и сделали в P0). Сущность `Task` в модели есть, но она НЕ является позвоночником ролевых экранов.
- **Парадокс:** тяжёлую заказную машину построили, а простой task-ориентированный Work-экран, который заявлен как суть продукта, — нет.
- **Что делать (после пилота):** решить стратегически — экран Work строится вокруг `Task` (раскрой/пошив/закупить/смонтировать), а не вокруг среза заказов. Это и есть «простота для сотрудника» из контекста. Сейчас не ломать (пилот поедет и на срезах), но это вектор №1.

## 🟡 Модель данных шире MVP

~30 сущностей. Контекст для MVP называет: Order, Task, Measurement, Material, Installation. Сверх этого: `FabricReservation`, `SeamstressPayment`, `ProductionLog`, `Cornice`/`Service` как отдельные, `TaskMeasurement`, `TaskHistory`, `OrderStatusHistory`, `ActivityLog`, `AppConfig`, `ProductionAssignment`. Часть оправдана, часть — на вырост.
- **Что делать:** не трогать на работающей БД, но при чистке FSM/сервисов не добавлять новых сущностей без ответа на вопрос «какую работу сотрудника это закрывает».

## 🟡 Реальные смlive-риски (не блокеры, но починить)

- **4× `except: ... pass` в сервисах** — молчаливое глотание ошибок. Например, в `transition_status_mvp` создание материалов из КП обёрнуто в `try/except: pass`: если упадёт — статус сменится, а материалы тихо не создадутся, и никто не узнает. → Логировать ошибку, а не глотать.
- **Легаси-статусы в FSM** (`draft/quoted/approved/...`) — путают и ломали тесты. Вычистить.
- **Mobile:** мёртвый `src/api/auth.ts` (несуществующие эндпоинты), демо-данные не за флагом, фоллбэк роли `owner`.
- **Frontend:** демо/прототип-страницы (`mvp-preview`, `product-demo`, `workflow-map`) вперемешку с боевыми.

## Что НЕ переусложнено (чтобы не выплеснуть полезное)

- Доменная модель заказа и операционные слои (`material_readiness`/`production_stage`/`handover_stage`) — по делу и совпадают с этапами ателье.
- `signals.py` для аудита — простой и рабочий.
- Сервисный слой как идея (логика вне вьюх) — правильно; проблема не в наличии сервисов, а в их объёме/дублях.
- P0/P1 (роли, срез, нумерация, JWT) — точечные и нужные.

## Приоритеты «упростить» (минимум риска → максимум эффекта)

1. **Вынести из MVP `events/` + `scheduler.py` + `task_generator.py`** (~5.3k строк). Это сразу снимает ~четверть когнитивной нагрузки и ничего не ломает (они не используются). — задача #17 расширяется.
2. **Убрать дубль инвентаря** (#18) и **депрекировать legacy `/api/`** (#20).
3. **Заменить `except: pass` на логирование** в сервисах (быстро, повышает диагностируемость).
4. После пилота — **развернуть Work вокруг `Task`**, как в `PROJECT_CONTEXT` (вектор продукта).

Принцип на будущее (твой же): прежде чем добавлять модуль — «какую конкретную работу сотрудника он закрывает?». Если ответа нет — в `future/`, не в MVP.
