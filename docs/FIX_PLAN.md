# БЛОК P0 — доступ и безопасность (делать первым, целиком)

## Шаг 1. Единый реестр ролей — починить имена групп
🎯 Создать `atelier_erp/roles.py` с каноничными именами и переписать на него все три места, где роли сейчас задаются вразнобой.

Каноничные роли (по твоей бизнес-модели, 5 штук):
`Owner` (Владелец/Админ — одно лицо), `Designer`, `Warehouse`, `Seamstress`, `Installer`.

Что синхронизировать:
1. `management/commands/seed_groups.py` — создавать ровно эти группы (сейчас `Manager`/`Installer`, нет `Owner`).
2. `api/permissions.py` — заменить `'Installation'` → `Installer`, убрать несуществующие `'Owner'` vs `'Manager'` разнобой и `'Worker'`.
3. `frontend/src/hooks/useRole.ts` — `GROUP_TO_ROLE` привести к тем же именам.
4. Data-migration: переименовать уже существующие группы в БД (`Manager`→`Owner`, и т.д.), иначе у текущих пользователей слетят группы.

⚠️ Сейчас проверки прав сравнивают строки, которые не совпадают с реально созданными группами → RBAC держится только на `is_superuser`. Пока это не починено, шаги 2 и 3 невозможно ни написать корректно, ни проверить.
✅ Завести по одному тест-пользователю на каждую роль. Под каждым убедиться: permission-классы пропускают/блокируют так, как задумано (например, `Installer` проходит `IsInstallationOrOwner`).
⏱ 0.5–1 день.

## Шаг 2. Срез заказов по ролям на бэкенде
🎯 Добавить `get_queryset()` с фильтром по группе в `OrderViewSet` (и в `/api/v1/`, и в legacy `/api/`). Убрать `total_amount/paid_amount/balance_due/customer_phone` из `OrderListSerializer` для непривилегированных ролей (либо отдельный «облегчённый» сериализатор).

Правило среза:
- Полный список — только `Owner` и `Designer`.
- `Warehouse` — заказы в статусах in_work / in_production / ready.
- `Seamstress` — только in_production.
- `Installer` — ready / on_installation / waiting_final_payment.
- Остальные — пусто.

⚠️ Сейчас любой авторизованный (склад, цех, монтаж) через `GET /api/v1/orders/` видит ВСЕ заказы с суммами и телефонами. Это утечка коммерческих и персональных данных и прямое нарушение требования «каждый видит свой срез». Фронтовый редирект не защищает — API дёргается напрямую.
✅ Тест: под `Warehouse`-пользователем `GET /orders/` возвращает только его срез и без финполей; под `Owner` — всё. Добавить эти тесты в `tests/`.
⏱ 1 день. **Зависит от шага 1.**

## Шаг 3. Default deny вместо дефолтного «owner»
🎯 На фронте (`useRole.ts`) и на бэке убрать фоллбэк «нет группы → owner». Нет группы → нет доступа: фронт ведёт на страницу «нет прав», бэк отдаёт `queryset.none()` и запрещает запись.

⚠️ Сейчас новый или неверно настроенный аккаунт получает полные права владельца. Тихая эскалация привилегий.
✅ Пользователь без группы не видит ни заказов, ни денег, не может создавать/менять.
⏱ 0.5 дня. **Зависит от шага 1.**

## Шаг 4. Безопасность конфигурации (settings)
🎯 `DEBUG` по умолчанию `False`; блок прод-настроек (`SECURE_SSL_REDIRECT`, `SESSION_COOKIE_SECURE`, `CSRF_COOKIE_SECURE`, `SECURE_HSTS_SECONDS`, `SECURE_PROXY_SSL_HEADER`); `ALLOWED_HOSTS` и `CORS_ALLOWED_ORIGINS` строго из окружения, без зашитых `0.0.0.0` и ngrok.

⚠️ При `DEBUG=True` любой 500 отдаёт стектрейс с кодом и переменными окружения. Cookie по HTTP → перехват сессии.
✅ На прод-стенде 500 показывает дефолтную страницу без трейса; cookie идут с `Secure`; запрос с чужого хоста отклоняется.
⏱ 0.5 дня. Независим — можно делать параллельно с 1–3.

> Конец P0 = система больше не «все видят всё» и не сыпет секретами. Только после этого можно сажать реальных сотрудников.

# БЛОК P1 — надёжность данных

## Шаг 5. PostgreSQL вместо SQLite
🎯 Перевести прод на PostgreSQL, убрать `db.sqlite3` из репозитория (`.gitignore` + `git rm --cached`), прогнать миграции на чистой PG-базе.
⚠️ SQLite под одновременной работой офиса+склада+цеха даёт `database is locked` и теряет записи.
✅ Все миграции применяются на PG; нагрузочный прогон параллельных запросов без блокировок.
⏱ 0.5–1 день.

## Шаг 6. Атомарная нумерация заказов
🎯 Заменить `count()+1` на атомарный счётчик (`select_for_update` по таблице-секвенсу за год или sequence в БД).
⚠️ Параллельные создания дают одинаковый номер → уникальный constraint → 500.
✅ Тест: 50 параллельных созданий → 50 уникальных номеров, без ошибок.
⏱ 0.5 дня.

## Шаг 7. JWT: отзыв + throttling логина
🎯 Подключить `token_blacklist`, включить ротацию и blacklist, сделать серверный logout. Добавить throttle на `/api/auth/token/`.
⚠️ Сейчас токен нельзя отозвать (увольнение/утечка = доступ до 7 дней), и логин открыт для брутфорса.
✅ После logout старый refresh не работает; >N попыток логина с IP → 429.
⏱ 0.5–1 день.

## Шаг 8. Производительность списков (N+1)
🎯 `select_related('customer')` в списках, `prefetch_related` в detail.
⚠️ На 100k заказов список = тысячи запросов.
✅ `django-debug-toolbar`/лог: число SQL-запросов на список не растёт с числом строк.
⏱ 0.25 дня. (Частично уже закрывается кодом из шага 2.)
