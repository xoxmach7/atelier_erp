# M2.2 — Авторасчёт метража ткани и тюля из замеров

**Дата:** 2026-07-11
**Статус:** дизайн утверждён, готов к плану реализации
**Область:** backend (`Measurement`, сериализатор, миграция), mobile (`MeasurementForm`, `quote.tsx`)

## Проблема

Сейчас метраж ткани (`curtain_meters`/`tulle_meters`) хранится на замере как обычные записываемые поля, а стоимость позиций КП вводится вручную в `mobile/app/orders/[id]/quote.tsx`. Метраж по факту не считается — его либо вводят руками, либо он остаётся нулевым. Цель M2.2 — **вычислять метраж из реальных замеров** (ширина окна × коэффициент сборки), которые вводит замерщик/установщик или дизайнер со слов клиента.

**Из области исключено:** автоматический расчёт *стоимости*. Цена позиций КП остаётся ручным вводом (решение пользователя). Тарифы `SewingRates`/`GatheringRatios` из `constants.py` в этой задаче не используются как источник цен.

## Решения (зафиксированы в брейнсторме)

1. **Метраж — производное от замеров**, не ручной ввод. Формула по модели «сборка»: метраж гонится по ширине окна с коэффициентом сборки; высота окна в погонный метраж не входит (уходит в раскрой по ширине рулона).
2. **Коэффициент сборки — настраиваемый на каждое окно**, не хардкод в коде. Хранится на замере.
3. **Раздельные коэффициенты** для шторы и тюля (по умолчанию разные, на практике собирают по-разному).
4. **Расчёт на бэкенде** при сохранении замера — единый источник истины для мобилки, веба и PDF. Никакого дублирования формулы в TypeScript.
5. **Округление вверх до 0.1 м** как дефолт (ткань нельзя купить «меньше»). Вынесено в одну функцию — легко поменять под конкретное ателье.

## Формула

```
curtain_meters = ceil_0.1(width_cm × curtain_gathering / 100)   если выбрана curtain_fabric, иначе 0
tulle_meters   = ceil_0.1(width_cm × tulle_gathering   / 100)   если выбрана tulle_fabric,   иначе 0
```

где `ceil_0.1(x)` — округление вверх до ближайших 0.1 м.

Пример: окно 300 см, сборка шторы 2.2 → `300 × 2.2 / 100 = 6.6 м`. Тюль 2.0 → `6.0 м`.

## Изменения — backend

### Модель `Measurement` (`atelier_erp/models.py`)

Добавить два поля:

```python
curtain_gathering = models.DecimalField(max_digits=4, decimal_places=2, default=Decimal('2.2'))
tulle_gathering   = models.DecimalField(max_digits=4, decimal_places=2, default=Decimal('2.0'))
```

Поля `curtain_meters` / `tulle_meters` остаются в модели (тип не меняется), но становятся **вычисляемыми выходами** — заполняются сервером, не клиентом.

### Расчёт метража

Единая функция (например `compute_meters(width_cm, gathering, has_fabric)`), возвращающая `Decimal`, с округлением вверх до 0.1 м. Одно место — точка изменения правила округления.

Вызывается при сохранении замера в `MeasurementSerializer.create()` / `.update()`: из валидированных `width_cm`, `curtain_gathering`, `tulle_gathering` и наличия `curtain_fabric` / `tulle_fabric` вычислить и записать `curtain_meters` / `tulle_meters`.

### Сериализатор и write-path (реальная архитектура)

Мобильный write-path идёт **не** через `MeasurementSerializer`, а через action
`POST /api/v1/orders/{id}/measurements/` (`OrderViewSet.measurements`), который
использует упрощённый `MeasurementCreateSerializer` (`atelier_erp/api/v1/serializers.py`).
Веб использует отдельный endpoint `/api/v1/measurements/` (`MeasurementViewSet` →
`MeasurementWriteSerializer`) — в этой задаче не мигрируется (web по-прежнему шлёт метраж вручную).

- `MeasurementCreateSerializer`: заменить одиночные `fabric_type`/`fabric_meters`/`fabric_name`
  на раздельные `curtain_fabric_name` + `curtain_gathering` и `tulle_fabric_name` + `tulle_gathering`.
  Метраж клиент не присылает.
- Action `measurements`: резолвит обе ткани по имени, вычисляет `curtain_meters`/`tulle_meters`
  через `compute_meters`, сохраняет вместе с коэффициентами сборки.
- Read-сериализатор `MeasurementSerializer` (v1) — добавить `curtain_gathering`/`tulle_gathering`
  в выдачу (задел под будущий edit-префилл; сами формы пока create-only).

### Миграция

Одна миграция: два новых поля с дефолтами. Существующие замеры получат дефолтные коэффициенты; их `*_meters` не пересчитываются задним числом автоматически (пересчитаются при следующем сохранении). Отдельного data-миграционного пересчёта не делаем — пилот с одним клиентом, исторические замеры не критичны.

## Изменения — mobile

### `MeasurementForm`

- Два поля коэффициента сборки, каждое рядом со своим выбором ткани:
  - **Сборка шторы** — выпадашка с пресетами `1.5 / 2.0 / 2.2 / 2.5`, дефолт `2.2`; активна, когда выбрана ткань шторы.
  - **Сборка тюля** — то же, дефолт `2.0`; активна при выбранной ткани тюля.
- Форма **перестаёт слать** `curtain_meters` / `tulle_meters`; вместо этого шлёт `curtain_gathering` / `tulle_gathering` + `width_cm`.
- **Живая подсказка** под полем ширины: `≈ X.X м` для шторы и тюля — та же формула локально, только для превью (источник истины остаётся бэкенд).
- Это попутно закрывает **M2.1**: тюль (ткань + коэффициент) уходит в свои поля модели, а не в `notes`.

**Важно:** есть второй, легаси-экран замера `mobile/app/orders/[id]/measurements.tsx` (список + своя inline-форма, дизайн-токены до Figma), тоже вызывающий `createMeasurement`. Его форму нужно мигрировать на новый payload синхронно, иначе он молча перестанет сохранять ткань (бэк больше не принимает `fabric_type`/`fabric_meters`).

### `mobile/app/orders/[id]/quote.tsx`

Практически без изменений — уже читает и показывает `curtain_meters` / `tulle_meters`. Цена остаётся ручным вводом. Проверить, что метраж отображается корректно теперь, когда он всегда посчитан сервером.

## Тесты

**Backend:**
- Формула метража: округление вверх до 0.1 м; нулевой метраж при отсутствии ткани; пересчёт при смене коэффициента.
- Сериализатор: `curtain_meters`/`tulle_meters` read-only (присланные клиентом значения игнорируются); `curtain_gathering`/`tulle_gathering` принимаются и влияют на метраж.

**Mobile:**
- Форма замера шлёт `curtain_gathering`/`tulle_gathering` и **не** шлёт `*_meters`.
- Живая подсказка показывает корректный расчётный метраж.

## Контракт API (итог)

`POST/PUT /api/v1/orders/{id}/measurements/` (через `MeasurementSerializer`):

| Поле | Направление | Примечание |
|------|-------------|-----------|
| `width_cm`, `height_cm` | вход | как раньше |
| `curtain_fabric`, `tulle_fabric` | вход | как раньше |
| `curtain_gathering`, `tulle_gathering` | вход (новое) | дефолты 2.2 / 2.0 |
| `curtain_meters`, `tulle_meters` | **только выход** | вычисляются сервером |

## Риски / открытые вопросы

- Правило округления у разных ателье различается — зафиксирован дефолт (вверх до 0.1 м) в одной функции, менять тривиально.
- Исторические замеры не пересчитываются при миграции — приемлемо для пилота с одним клиентом.
