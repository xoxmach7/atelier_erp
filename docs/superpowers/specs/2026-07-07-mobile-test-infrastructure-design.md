# Mobile: тестовая инфраструктура + покрытие API-слоя — дизайн

> Часть 1 из 3 независимых под-проектов по улучшению мобилки (согласовано с владельцем 2026-07-07):
> 1. **Тестовая инфраструктура + API-слой** (этот документ) — делается первым, как страховочная сетка перед рефакторингом.
> 2. Разбить `mobile/src/api/orders.ts` на файлы по домену — следующий шаг.
> 3. Подключить роли Швея/Монтажник к реальному API — см. `docs/superpowers/specs/2026-07-07-mobile-production-installer-screens-design.md`.
>
> Компоненты и экраны (широкое покрытие) — сознательно вне рамок этого документа, будут отдельными спеками после того, как API-слой покрыт и стабилен.

## Проблема

В `mobile/` (Expo SDK 54, RN 0.81, React 19) нет ни тестового фреймворка, ни единого теста — ни юнит-, ни интеграционного. `package.json` не содержит `jest`/`@testing-library/react-native` ни в зависимостях, ни в `devDependencies`, ни скрипта `test`.

Это значит, что любой рефакторинг (включая уже запланированное разбиение `api/orders.ts` и подключение ролей Sewing/Install) делается вслепую — единственная защита от регрессий сейчас — это TypeScript-компилятор (`npm run typecheck`) и ручное тестирование на устройстве.

## Почему начинаем с API-слоя, а не с компонентов/экранов

- `mobile/src/api/*.ts` (7 файлов: `client.ts`, `orders.ts`, `customers.ts`, `fabrics.ts`, `payments.ts`, `staff.ts`, `work.ts`) — чистые функции без UI, не требуют рендеринга React-дерева, самые дешёвые и быстрые для покрытия.
- `client.ts` (152 строки) содержит самую критичную для бизнеса логику: retry на 401 с обновлением токена, дедупликация параллельных refresh-запросов, обработка сетевых ошибок, различие JSON/FormData body. Баг здесь означает разлогин сотрудника посреди работы или потерю данных при отправке фото/акта — именно такая цена регрессии оправдывает тесты в первую очередь.
- Дизайн/компонентные тесты дают меньше уверенности на вложенный доллар при таком объёме первоначального долга — их логичнее делать после того, как есть рабочий Jest-конфиг и понятный паттерн (эта задача его создаёт).

## Дизайн

### 1. Стек

- **`jest-expo`** — официальный Jest-пресет от команды Expo, знает про трансформацию native-модулей (`expo-*` пакеты), совместим с Expo SDK 54.
- **`@testing-library/react-native`** — устанавливается в этой задаче (как devDependency), хотя явно не используется здесь (нет компонентных тестов в этом под-проекте) — установка сразу избавляет от повторной настройки конфигурации в под-проекте 3 (компоненты/экраны), где он понадобится.
- **`@react-native-async-storage/async-storage/jest/async-storage-mock`** — официальный мок пакета, уже используемого в `client.ts`.
- **`ts-jest`** не нужен отдельно — `jest-expo` уже поддерживает TypeScript через babel-transform, соответствующий существующему `babel-preset-expo` в проекте.

### 2. Конфигурация

- `mobile/jest.config.js` (или секция `"jest"` в `package.json` — выбрать при реализации по консистентности с остальным проектом, конкретики от `jest-expo` README) с `preset: 'jest-expo'`.
- Добавить в `mobile/package.json`:
  - `devDependencies`: `jest-expo`, `@testing-library/react-native`, `@types/jest`.
  - `scripts.test`: `jest`.
- `global.fetch` не мокается глобально в конфиге — каждый тест-файл сам устанавливает `jest.fn()` на `global.fetch` в `beforeEach`, чтобы избежать утечки состояния между тестами (явное лучше неявного).

### 4. Покрытие `client.ts` (приоритет — самая важная часть)

Обязательные сценарии (список, не псевдокод — точные assert'ы пишутся на этапе реализации по TDD):
1. `get`/`post`/`patch`/`del` формируют правильный URL (`baseUrl + endpoint`), метод, и `Authorization: Bearer <token>` header, когда токен есть в `AsyncStorage`.
2. Без токена в `AsyncStorage` — запрос уходит без `Authorization` header (не `Bearer undefined`/`Bearer null`).
3. `postMultipart` с `FormData` телом — не выставляет `Content-Type: application/json` (should let fetch/RN set the multipart boundary itself).
4. `POST`/`PATCH` с обычным телом — сериализуют его в JSON и выставляют `Content-Type: application/json`.
5. Ответ `401` → вызывается `refreshAccessToken` (проверить вызов `POST /api/auth/token/refresh/` с текущим refresh-токеном) → при успехе (новый `access` в ответе) исходный запрос повторяется **один раз** с новым токеном (`retry=false` на втором заходе — тест должен проверить, что при повторном 401 после успешного refresh нет второй попытки refresh, а сразу бросается ошибка, если второй запрос тоже вернул 401 — маловероятный, но проверяемый edge case).
6. Два параллельных запроса, оба получившие `401` одновременно — должны вызвать `refreshAccessToken` **один раз** (проверка на `refreshPromise`-дедупликацию, не двух параллельных POST на `/refresh/`).
7. Refresh возвращает не-ok ответ → `AsyncStorage` очищается (`access`, `refresh`, `atelier_user` все три ключа), вызывается зарегистрированный `onUnauthorized` callback (через `setUnauthorizedCallback`), выбрасывается `ApiError{status: 401, message: 'Сессия истекла. Войдите снова.'}`.
8. `fetch` бросает исключение (симуляция обрыва сети) → перехватывается, выбрасывается `ApiError{status: 0, message: содержит baseUrl}` — не даёт необработанному исключению всплыть наружу.
9. Ответ с `!response.ok` (не 401, например 400/500) → парсит JSON тело, использует `detail`/`error` поле для `message`, либо fallback `Ошибка сервера: HTTP <status>`, если тело не парсится.
10. Ответ `204 No Content` → возвращает `{}`, не пытается вызвать `.json()` на пустом теле (это бы бросило `SyntaxError` в реальном `fetch`, поэтому мокнутый `Response` в тесте должен явно проверять, что `.json()` не вызывается при 204).

### 5. Покрытие остальных модулей (`orders.ts`, `customers.ts`, `fabrics.ts`, `payments.ts`, `staff.ts`, `work.ts`)

Для каждой экспортируемой функции модуля — один тест, мокающий **сам `apiClient`** (не `fetch` — `client.ts` уже покрыт изолированно, дублировать его внутреннюю логику здесь не нужно). Проверяется:
- Функция вызывает правильный метод (`apiClient.get`/`post`/`patch`/`del`/`postMultipart`) с правильным endpoint (включая интерполяцию `id` в путь, где применимо).
- Функция передаёт правильное тело запроса (для `post`/`patch`).
- Функция возвращает то, что вернул мокнутый `apiClient` (без дополнительной трансформации, если её нет в реальном коде — если трансформация есть, тест её проверяет).

**Явно не тестируем:** сами TypeScript-интерфейсы (компилятор это гарантирует), реальные HTTP-запросы (у нас нет соглашения о поднятии тестового backend в CI на этом этапе — вне рамок).

### 6. Критерий готовности

- `npm test` (новый скрипт) проходит зелёным, 0 failures.
- `npm run typecheck` остаётся на 0 ошибок (как и было).
- Каждая экспортируемая функция из всех 7 файлов `mobile/src/api/*.ts` имеет минимум один тест.
- `client.ts` — все 10 сценариев выше покрыты.

## Явно вне рамок этого под-проекта

- Тесты компонентов (`mobile/src/components/*.tsx`) и экранов (`mobile/app/**/*.tsx`) — следующий под-проект после того, как этот стабилизируется и даст паттерн для переиспользования.
- CI-интеграция (GitHub Actions запуск тестов на PR) — не обсуждалось с владельцем, отдельное решение.
- E2E-тесты (Detox/Maestro) — не обсуждались, отдельный масштаб решения.
- Изменение поведения `client.ts` или любого API-модуля — эта задача **только добавляет тесты** к существующему коду, не меняет логику. Если тест обнаружит расхождение с ожидаемым поведением — это фиксируется отдельным багом/задачей, не тихо чинится в рамках написания тестов.
