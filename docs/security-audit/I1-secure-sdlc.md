# I1 — Secure SDLC & Deployment

Дата: 2026-07-20. Источники: `find .github`, `.pre-commit-config.yaml` (отсутствует), `.git/hooks` (только `*.sample`), `Dockerfile`, `docker-compose.yml`, история дефис-аудитов в `CLAUDE.md` (dependency audit 2026-07-11).

## 1. Текущий пайплайн

**CI/CD в общепринятом смысле не существует.** `.github/workflows` — нет такой директории вообще (не пустая — отсутствует), pre-commit hooks не настроены, `.git/hooks` содержит только образцы (`*.sample`), которые Git ставит по умолчанию и никто не активировал.

| Этап | Как происходит сейчас |
|---|---|
| Тесты (backend/frontend/mobile) | Запускаются **вручную** в сессиях с Claude Code или разработчиком; нет автозапуска на push/PR |
| Security-проверки (SAST, dependency scanning, secret scanning) | Не автоматизированы. Dependency-аудит (`pip-audit`, `npm audit`) делался **разово вручную** в отдельных сессиях (2026-07-11), не на регулярной основе и не как гейт перед деплоем |
| Деплой | Push в `main` → Railway (backend) автодеплоит по git-интеграции; Vercel (фронтенд) аналогично по git-интеграции. Никакого review/approval-шага между push и продакшеном — `main` и есть прод. |
| Окружения | Только dev (локально, SQLite или `docker-compose.yml`, помечен как «staging», но по факту тот же код без изоляции от прод-конфига) и prod (Railway/Vercel). **Отдельного stage-окружения, изолированного от прода, нет.** |

## 2. Что это значит на практике

- Любой коммит в `main` уходит в прод немедленно, без промежуточного ревью специально для security-аспектов (обычный code review — да, но не автоматизированный гейт).
- Тесты **могут** быть зелёными локально и не запуститься перед деплоем вообще — ничто технически не мешает запушить с падающими тестами (не проверено человеческим процессом, а не автоматикой).
- Уязвимость в зависимости появится и провисит незамеченной до следующего разового ручного аудита — между аудитами 2026-07-11 и текущим (2026-07-20) прошло больше недели, в течение которых новый CVE в любой из зависимостей остался бы незамеченным.
- Секрет, случайно закоммиченный в код (даже по ошибке, `.env` вместо `.env.example`), ничем не перехватывается на этапе коммита/пуша — только `.gitignore`, который защищает от неё же самой ошибки, если файл уже был закоммичен раньше (не защищает от нового секрета в новом файле).

## 3. Риски

| Риск | Приоритет |
|---|---|
| **Нет автоматического security-гейта перед деплоем** (тесты, dependency scan, secret scan) — весь процесс держится на дисциплине человека, который может забыть/поспешить. | **High** |
| **Нет regression-защиты для тестов** — падающий тест не блокирует деплой технически. | **Medium-High** |
| **Нет secret-scanning** (gitleaks/trufflehog и подобные) — единственная защита от случайного коммита секрета — `.gitignore`, который не помогает, если секрет уже один раз попал в историю. | **Medium** |
| **Нет staging-окружения** — новый код тестируется либо локально (не прод-конфигурация: SQLite вместо Postgres, `DEBUG` часто `True`), либо сразу в проде. | **Medium** |
| Зависимости проверяются только вручную, эпизодически | **Medium** |

## 4. Рекомендации

Самый дешёвый по трудозатратам, но наиболее ценный первый шаг — простой GitHub Actions workflow (даже без глубокого SAST) на каждый push/PR в `main`:

1. `python manage.py test --settings=atelier_erp.settings_test` (backend) — уже существует и зелёный (204 теста), просто не запускается автоматически.
2. `npm test -- --run` (frontend), `npx jest` (mobile) — то же самое, тесты уже есть.
3. `pip-audit` / `npm audit --audit-level=high` — как проверка, не обязательно блокирующая на старте (можно начать с warn-only, потом сделать gate).
4. Секрет-сканирование (gitleaks — однострочный шаг в workflow) на diff пуша.

Дальше, не сразу: staging-окружение (отдельный Railway-сервис с PostgreSQL, деплоящийся из ветки, отличной от `main`) — оправдано, когда появится второй/третий клиент и цена ошибки в проде вырастет.

Approval-флоу для прод-деплоя (кто-то должен подтвердить перед мержем в `main`) — пока команда состоит из одного человека, это неприменимо; станет актуальным при найме второго разработчика.
