# D1 — Network & Segmentation (managed PaaS)

Дата: 2026-07-20. Стек: Django на Railway (Gunicorn + WhiteNoise), Next.js на Vercel, PostgreSQL — Railway-managed add-on, медиа — Cloudflare R2. **Нет VPS, нет самостоятельно управляемого Nginx/файрвола** — весь сетевой периметр либо у платформ, либо решается настройками Django (`ALLOWED_HOSTS`, CORS/CSRF).

Источники: `settings.py`, `Dockerfile`, memory `project_railway_deploy` (сверено `railway status`/`railway variables` 2026-07-11 и 2026-07-18).

## 1. Граница ответственности (shared responsibility)

| Контроль | Кто отвечает | Комментарий |
|---|---|---|
| TLS-терминация (HTTPS) | Railway / Vercel | `SECURE_PROXY_SSL_HEADER` в `settings.py` доверяет заголовку от прокси платформы — стандартно для PaaS |
| DDoS-защита на уровне сети | Railway / Vercel | Не настраивается из кода, это уровень платформы |
| Изоляция контейнеров/сетевых namespace | Railway | Приложение не видит и не управляет этим слоем |
| Приватная сеть между backend и Postgres | Railway (`postgres.railway.internal`) | **Уже используется правильно** — `DB_HOST` в проде указывает на internal-хостнейм, обычный трафик приложение↔БД никогда не выходит наружу |
| Firewall / security groups / allowed ports | Не применимо — Railway не даёт (и не требует) ручной настройки файрвола для managed-сервисов | Компенсирующий контроль — `ALLOWED_HOSTS`/CORS/CSRF на уровне Django (см. ниже) |
| Кто смотрит из интернета на что | Приложение (частично) | `/api/v1/`, `/admin/`, `/health/` — всё на одном публичном домене Railway (`ateliererp-production.up.railway.app`), нет отдельного внутреннего/внешнего разделения путей |

## 2. Что реально смотрит в интернет

| Сервис | Публичный доступ | Чем защищено |
|---|---|---|
| Django backend (весь `/api/v1/`, `/admin/`, `/health/`) | Да, один и тот же домен и порт для всего | JWT/сессия + `ALLOWED_HOSTS` (whitelist из env) — нет разделения «публичный API» / «внутренний admin» на сетевом уровне, только на уровне логина |
| Next.js фронтенд | Да, Vercel | Стандартная защита Vercel, статический контент + серверные вызовы к backend API |
| PostgreSQL — внутренний путь | **Нет** (только `postgres.railway.internal`, недостижим извне) | Правильно изолирован |
| **PostgreSQL — публичный прокси (`DATABASE_PUBLIC_URL`)** | **Да.** Railway создаёт публичный TCP-эндпоинт для Postgres-аддона (`acela.proxy.rlwy.net:<port>`) по умолчанию, вне зависимости от того, используется он или нет. Использовался вручную для one-off операций (сиды на проде, 2026-07-18). | Единственная защита — пароль БД внутри строки подключения. Никакого IP-allowlist на этом прокси не настраивалось (не проверялось, поддерживает ли Railway такую опцию для этого плана). | 
| Cloudflare R2 (медиа) | Да, но через подписанные URL (TTL 1 час) | Не голый bucket — нужен подписанный запрос |

## 3. Входящие/исходящие потоки

**Входящие:** только через Railway/Vercel edge → Django/Next.js. Никакого второго входа (нет отдельного admin-поддомена, VPN, bastion-хоста).

**Исходящие (egress) от backend:** единственный внешний вызов — к Cloudflare R2 (`AWS_S3_ENDPOINT_URL`) для чтения/записи/подписи медиафайлов. Нет вызовов к email/SMS/платёжным API (не настроены, см. B1). Проверена и ранее закрыта SSRF-поверхность в генерации PDF КП (`_link_callback` в `quote_service.py`, ограничен локальными шрифтами, фикс 2026-07-11) — это единственное место в коде, где когда-либо был потенциал резолвить произвольный внешний URI.

## 4. Риски

| Риск | Разбор | Приоритет |
|---|---|---|
| **`DATABASE_PUBLIC_URL` — постоянно существующий публичный вход в БД в обход всего приложения.** | Дублирует находку B2, здесь — с сетевой стороны: это не временная опция «включили на час для сида», а всегда доступный Railway-эндпоинт. Утечка пароля БД (через логи, через историю `railway variables`, через компрометацию рабочей машины, с которой запускали сиды) = полный доступ ко всем данным всех тенантов без прохода через RBAC/tenant-скоуп/JWT вообще. | **High** |
| **API и admin на одном публичном пути без сетевого разделения.** | `/admin/` доступен с того же домена, что и `/api/v1/` — компенсируется только логином (сессия Django), не сетевой изоляцией. На managed PaaS это ожидаемо (нет второго origin бесплатно), но стоит знать, что «спрятать» admin от интернета сетевыми средствами сейчас нельзя — вся защита на уровне пароля/будущего MFA (см. C1). | **Medium** (пересекается с C1) |
| **Нет проверенного egress-allowlist.** | Backend технически может обратиться куда угодно из кода (нет сетевого файрвола, ограничивающего исходящие соединения) — единственная защита от SSRF/exfiltration через код, а не через сеть. Один найденный вектор (PDF `_link_callback`) уже закрыт; новый код с пользовательским URL (например, будущая интеграция с мессенджерами для лидов, см. предыдущую задачу Sales CRM) должен ревьюситься на этот случай явно, т.к. сетевого второго рубежа нет. | **Low-Medium**, архитектурная памятка на будущее |
| **Нет отдельного изолированного stage/QA окружения.** | Согласно `.env.example`/`settings_test.py` — есть только dev (SQLite/local) и prod (Railway). Тестирование безопасности/нагрузки против прод-подобного окружения без риска для реальных данных сейчас невозможно без создания отдельного Railway-сервиса. | **Low** на текущем масштабе (1 пилотный клиент), но стоит учесть в I1/roadmap |

## 5. Рекомендации

1. **Проверить, можно ли отключить публичный TCP-прокси Postgres на плане Railway**, оставив доступ только через `railway connect`/`railway run` (внутри их сети) или через временное включение прокси только на время операции, а не постоянно. Если отключить нельзя — минимум сменить пароль БД после каждой ручной операции через публичный прокси и не хранить `DATABASE_PUBLIC_URL` в истории команд/логах дольше необходимого.
2. **Компенсирующие контроли уже в целом на месте и корректны** для PaaS-модели: `ALLOWED_HOSTS`, `CORS_ALLOWED_ORIGINS`, `CSRF_TRUSTED_ORIGINS` — все явно из env, без LAN-дефолтов (фикс P4-CFG). Ничего срочно менять здесь не нужно.
3. Когда появится вторая реальная интеграция с исходящими вызовами (мессенджеры, email) — заводить её с explicit allowlist домена в коде (не полагаться на «сети всё равно нет», раз файрвола нет и не будет).
