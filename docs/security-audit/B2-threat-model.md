# B2 — Threat Model (STRIDE)

Дата: 2026-07-20. Опирается на карту из [B1-architecture.md](B1-architecture.md). Дополнительно прочитаны `api/permissions.py`, `api/auth_views.py`, `settings.py` (throttling/cache), `ensure_superuser.py`.

Правило этого документа: если угроза уже закрыта конкретным фиксом из `CLAUDE.md` — она перечислена в разделе «Уже закрыто» как **контроль**, а не как открытая угроза. Открытые угрозы — только то, что реально не проверялось или не чинилось раньше.

## 1. Активы

| Актив | Где живёт | Чувствительность |
|---|---|---|
| Учётные данные (пароли, JWT) | PostgreSQL (хэши), клиенты (токены) | Высокая — компрометация = полный доступ к роли/тенанту |
| ПДн клиентов ателье (ФИО, телефон, адрес) | `Customer` в PostgreSQL | Высокая — персональные данные третьих лиц (не пользователей системы) |
| Деньги (суммы заказов, платежи) | `Order`, `Payment` | Высокая — прямой финансовый эффект при подделке |
| Фото объектов / подписанные АВР | Cloudflare R2 | Средняя — конфиденциальность жилья клиентов, юридическая значимость АВР |
| Данные одного тенанта относительно другого | Всё вышеперечисленное, разграничено `tenant` | Высокая — межтенантная утечка = утечка данных чужого бизнеса целиком |
| Секреты инфраструктуры (`DJANGO_SECRET_KEY`, R2-ключи, `DATABASE_PUBLIC_URL`, `SUPERUSER_PASSWORD`) | Railway/Vercel env vars | Критическая — компрометация одного из них обычно даёт доступ ко всей системе |

## 2. STRIDE по компонентам

### 2.1 Backend API (Django/DRF)

| Угроза | Разбор | Приоритет |
|---|---|---|
| **Spoofing** — подбор пароля (брутфорс логина) | Throttle `login: 5/min` есть, но кеш DRF-throttling — **дефолтный `LocMemCache`** (в `settings.py` нет блока `CACHES`). Gunicorn поднят с `--workers 3` (`Dockerfile`) — у каждого воркера своя память, значит счётчик throttle не общий: реальный лимит брутфорса ближе к **15/мин**, а не 5/мин, и сбрасывается при рестарте/redeploy воркера. То же самое ослабляет и `anon: 20/min`/`user: 200/min`. | **High** |
| **Spoofing** — компрометация единственного superuser (`admin`) | Пароль — обычный пароль без MFA, к тому же **пересоздаётся при каждом деплое** из `SUPERUSER_PASSWORD` (`ensure_superuser`, вызывается в `CMD` контейнера). Если пароль поменяли вручную через `/admin/` (например, в рамках ротации), следующий деплой молча откатит его на значение из env-переменной. Утечёт `SUPERUSER_PASSWORD` из Railway Variables — компрометация не лечится сменой пароля в UI, только сменой самой переменной. | **High** |
| **Tampering** — межтенантная подмена/чтение данных | Основная защита — `TenantManager` (ORM ContextVar) + `scope_to_tenant()`/`scope_orders_for_role()` на уровне DRF. Все известные экземпляры этой угрозы уже закрыты (см. «Уже закрыто» ниже). Архитектурный риск на будущее: `permissions.py` — почти сплошь `has_permission` (проверка роли), **не** `has_object_permission` (проверка «этот объект — правда мой»). Изоляция по объекту держится на дисциплине `get_queryset()` в каждом ViewSet, а не на permission-классе как второй линии защиты. Один забытый `scope_to_tenant()`/`scope_orders_for_role()` в новом эндпоинте — и объектной защиты не остаётся вообще (ровно так были найдены и закрыты `FinanceWorkQueueView`, `MeasurementViewSet`, `/v1/tasks/`, `/v1/customers/` — см. `CLAUDE.md`). Это системный, повторяющийся паттерн бага, не разовая опечатка. | **Medium** (паттерн, не конкретный открытый экземпляр) |
| **Tampering** — подделка суммы заказа/оплаты | В этой же сессии закрыты 2 связанных бага (не security, а data-integrity, но со security-эффектом «оплата обходится тривиально» — заказ завершался с `paid_amount=0`). Уже пофикшено: `total_amount` синхронизируется с КП, `PaymentViewSet` идёт через `PaymentService.record_payment`. | Закрыто в этой сессии |
| **Repudiation** — отрицание действия («я не менял статус/не одобрял КП») | `OrderStatusHistory`/`ActivityLog` фиксируют `changed_by`/`performed_by`, автопереходы помечены префиксом `[авто]`. Но это обычные Django-модели без запрета на `UPDATE`/`DELETE` — ничто на уровне БД не мешает переписать историю задним числом при получении доступа к БД (например, через утёкший `DATABASE_PUBLIC_URL`). Не критично при текущем масштабе (один тенант, доверенная команда), но стоит иметь в виду при росте. | **Low** |
| **Information Disclosure** — утечка деталей ошибок | Закрыто (`_safe_error`, аудит 2026-07-19) — клиент получает обобщённый текст, стек уходит в лог. | Закрыто |
| **Information Disclosure** — browsable DRF API в проде | `/api/auth/` (`rest_framework.urls`) подключён без проверки `DEBUG` — в проде доступна HTML-форма логина DRF и browsable API (не сам данные, но раскрывает структуру API/serializer-ошибки подробнее, чем JSON-клиент). Осознанного решения «нужно ли это в проде» не зафиксировано. | **Low-Medium** |
| **Denial of Service** — исчерпание ресурсов | Общий rate-limit есть (ослаблен из-за LocMemCache, см. выше). Лимиты на размер файлов есть (10MB фото, 20MB АВР). Нет отдельной защиты от DoS на уровне приложения (это по большей части ответственность платформы — Railway/Vercel, см. D1). | Частично закрыто, зависит от D1 |
| **Elevation of Privilege** — эскалация роли | RBAC держится на едином `roles.py`, `user_in()` понимает legacy-алиасы. Все обнаруженные конкретные дыры (замеры, справочники, платежи, КП) закрыты по датам в `CLAUDE.md`. Остаточный риск — тот же паттерн, что в Tampering выше: RBAC у вас **decorator-style** (проверка в каждом ViewSet), не декларативный на уровне модели/роутера — цена ошибки в новом коде высокая. | **Medium** (паттерн) |

### 2.2 Веб-фронтенд (Next.js на Vercel)

| Угроза | Разбор | Приоритет |
|---|---|---|
| **Spoofing/Tampering** — XSS, `dangerouslySetInnerHTML`, `eval` | Проверялось в аудите 2026-07-11 («Client-side + инфра security review») — чисто. Не проверялось повторно в рамках B2. | Закрыто (на дату прошлой проверки) |
| **Information Disclosure** — где хранится JWT в браузере | **Не проверено ни разу.** localStorage vs httpOnly-cookie vs память — принципиально разный риск при XSS (localStorage читается любым инжектированным скриптом). Мобилка это уже прошла (`expo-secure-store`), веб — нет данных. | **High — перенести в E1** |
| **Tampering** — CSRF | DRF `SessionAuthentication` требует CSRF-токен на unsafe-методах; основной путь — JWT в заголовке, для которого CSRF неприменим по определению (не куки). Риска нет, пока веб не переключится на cookie-based JWT. | Низкий, не открыт |

### 2.3 Мобильное приложение (Expo)

| Угроза | Разбор | Приоритет |
|---|---|---|
| **Information Disclosure** — токены в незашифрованном хранилище | Закрыто 2026-07-11 — перенесены в `expo-secure-store`. | Закрыто |
| **Tampering** — подмена API-ответа / MITM | Base URL берётся из `EXPO_PUBLIC_API_BASE_URL`, TLS обеспечивает Railway. Certificate pinning не реализован (типично для MVP-стадии, не обязательно сейчас). | Low, к рассмотрению позже |
| **Spoofing** — дистрибуция приложения через Expo Go/EAS, не сторы | Означает, что нет App Store/Play Store review как доп. барьера, но и не публичный листинг — риск скорее в качестве сборки, не в security per se. | Инфо, не угроза |

### 2.4 База данных (PostgreSQL, Railway-managed)

| Угроза | Разбор | Приоритет |
|---|---|---|
| **Information Disclosure/Tampering** — `DATABASE_PUBLIC_URL` | Публичный (интернет-доступный) коннекшн-стринг к проду, использовался вручную для `seed_demo --reset` (см. `CLAUDE.md`, 2026-07-18). Кто угодно с этой строкой обходит **всё**: RBAC, tenant-скоуп, приложение целиком — прямой SQL-доступ. Единственная защита — секретность самой строки (пароль в ней) и, предположительно, отсутствие публичного IP-листинга со стороны Railway (не проверялось — см. D1). Это самая большая единичная точка отказа во всей системе. | **High** |
| **Tampering** — SQL injection | Подтверждено: `grep -rn "\.raw(\|\.extra(\|cursor\.execute"` по всему `atelier_erp/` — 0 совпадений. Весь доступ к БД идёт через Django ORM. | Закрыто (подтверждено) |

### 2.5 Файловое хранилище (Cloudflare R2)

| Угроза | Разбор | Приоритет |
|---|---|---|
| **Information Disclosure** — доступ к чужим файлам по URL | Подписанные URL, TTL 1 час, `AWS_QUERYSTRING_AUTH=True` — по срокам действия это разумно. Не проверялось: предсказуемость пути файла (последовательные ID vs UUID) — если путь предсказуем, TTL не спасает от простого перебора в течение часа. | Low-Medium, стоит подтвердить в E1 |
| **Tampering** — загрузка вредоносного файла под видом фото | Закрыто — валидация по magic bytes (не по расширению), обработка `SyntaxError`/`ValueError` от повреждённых файлов (2026-07-11/07-18). | Закрыто |

## 3. Сводный приоритет (для J1/roadmap)

| Приоритет | Угроза | Куда чинить |
|---|---|---|
| High | Throttle-кеш не общий между воркерами — брутфорс-защита слабее заявленной | Backend: настроить `CACHES` (даже `django-redis` не нужен — файловый/DB-кеш тоже общий между процессами, в отличие от LocMem) |
| High | `SUPERUSER_PASSWORD` пересоздаёт пароль на каждом деплое, нет MFA | F1 (секреты) / C1 (IAM) |
| High | `DATABASE_PUBLIC_URL` — полный обход приложения при утечке | D1 (сеть) — проверить, действительно ли строка постоянно активна или включается вручную только на время операции |
| Medium | RBAC/tenant-изоляция — паттерн «легко забыть scope в новом ViewSet», нет декларативной второй линии защиты | Архитектурный долг, не разовый фикс — возможный кандидат в J1 roadmap |
| Medium | Browsable DRF API включён в проде без явного решения | Быстрый фикс — не в скоупе B2 (это анализ, не фикс) |
| Medium | Где именно веб хранит JWT (localStorage?) | Переносится в E1 как обязательный пункт |
| Low | История статусов/аудит-лог не защищены от прямого изменения в БД | Не критично при текущем масштабе |
| Low | Предсказуемость путей файлов в R2 | Подтвердить в E1 |
