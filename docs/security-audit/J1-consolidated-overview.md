## 1. Целевая архитектура безопасности (кратко)

Система — монолит на управляемых платформах (Railway + Vercel + Cloudflare R2), без собственной сети/файрвола. Правильная модель угроз для такой системы — не «защита периметра», а:

1. **Единая точка входа (`/api/v1/`) с надёжной аутентификацией/авторизацией** — RBAC уже есть и в целом работает, но держится на дисциплине разработчика (`get_queryset()` в каждом ViewSet), а не на декларативной второй линии защиты.
2. **Секреты и учётки — единственный настоящий периметр.** При отсутствии сетевой изоляции всё сводится к тому, кто знает пароль/ключ. Отсюда: MFA для superuser, ротация секретов, разделение `DJANGO_SECRET_KEY`/JWT-ключа, закрытие `DATABASE_PUBLIC_URL`.
3. **Видимость (логи/аудит) как компенсация отсутствия сетевого мониторинга** — раз нет файрвола/IDS на сети, обнаружение атаки должно происходить на уровне приложения (логин-попытки, 403-отказы), чего сейчас почти нет.
4. **Automated security gate в CI** — при команде из одного человека это единственная защита от «забыл проверить перед деплоем».
5. **Проверенная возможность восстановления** — единственная защита от необратимой потери данных при отсутствии инфраструктурной избыточности.

## 3. Roadmap

**Сделать сейчас (до второго клиента), дёшево и весомо:**
- #5 (логирование неудачных логинов) — несколько строк кода.
- #1 (общий кеш для throttle) — одна настройка `CACHES`.
- #6 (проверить/включить бэкапы Railway + тест restore) — не код, но критично и дёшево.
- #7 (простой CI-воркфлоу с уже существующими зелёными тестами) — тесты уже написаны, не хватает только автозапуска.
- #2 (решить судьбу `ensure_superuser`-автосброса пароля) — однострочное решение (убрать вызов из `CMD` или явно задокументировать и дать MFA).

**Сделать в течение следующих спринтов:**
- #4 (JWT-хранение на вебе) — требует изменений на backend (выдача httpOnly-cookie) и фронте, нетривиально, но самый весомый пункт из «данных».
- #3 (`DATABASE_PUBLIC_URL`) — зависит от возможностей плана Railway, нужно сначала выяснить, что вообще доступно.
- #8, #10 (Owner-permissions в admin, разделение `SECRET_KEY`/JWT-ключа) — точечные, безопасные правки.
- #11 (регламент ротации секретов) — организационный документ, не код.

**Наблюдать / переоценить при росте (после 2–3 клиентов):**
- #14 (staging-окружение) — оправдано, когда цена ошибки в проде вырастет.
- #16 (архитектурный паттерн RBAC) — не переписывать превентивно, но держать в голове при добавлении каждого нового ViewSet; можно рассмотреть общий миксин/декоратор, который проверяет, что `scope_to_tenant()`/`scope_orders_for_role()` вызван, если появится третий похожий инцидент.
- #17 (разделение admin от публичного домена) — не first-class задача на PaaS без второго origin, переоценить при найме второго разработчика.
- #25 (SPOF на каждом уровне) — станет реальной проблемой только при заметном росте нагрузки/числа клиентов.

## 4. Допущения и остаточные риски

- **A1 (scope) не был формализован отдельным документом** — аудит охватил весь код и все окружения (dev/prod), но не проходил через явное подтверждение владельца, что именно критично для бизнеса и есть ли регуляторные требования (GDPR и т.п. — Sheber работает с ПДн клиентов ателье в Казахстане; применимость конкретных норм не оценивалась).
- **Backup/DR (H1) и организационные вопросы доступа (F1 §5) — за пределами того, что видно из кода.** Требуют прямой проверки в консолях Railway/Vercel/Cloudflare, не в репозитории.
- **Аудит не включал реального penetration-теста** (SQLi/XSS/auth-bypass через фактическую эксплуатацию) — все находки основаны на чтении кода/конфигурации, не на попытках взлома живой системы. Для системы с реальными платежами клиентов стоит рассмотреть внешний pentest при росте масштаба.
- **DEBUG/секреты/значения переменных в реальном Railway/Vercel окружении не читались** — аудит намеренно ограничился структурой кода, не содержимым `.env` в проде.
- Все находки уровня High/Medium не являются подтверждёнными эксплуатируемыми уязвимостями «уже произошедшими» — это архитектурные риски и пробелы в защите, приоритизированные по вероятному ущербу при реализации.
