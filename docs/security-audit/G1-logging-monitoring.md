# G1 — Logging, Monitoring & Audit

Дата: 2026-07-20. Источники: `settings.py` (`LOGGING`), `grep` по `logger\.` во всём `atelier_erp/`, `signals.py`, модели `ActivityLog`/`OrderStatusHistory`/`TaskHistory`, Django `admin.LogEntry` (встроенный).

## 1. Что логируется сейчас

| Категория | Есть? | Где |
|---|---|---|
| Необработанные ошибки API (`except Exception`) | Да | `_safe_error()` в `api/v1/views.py` — `logger.exception(...)` со стеком, клиенту уходит обобщённый текст (фикс 2026-07-19) |
| Автопереходы статуса заказа | Да | `status_automation.py` — `logger.info` на каждую попытку (успех и молчаливый отказ) |
| Создание материалов из КП без approved-квоты | Да | `order_service.py:561` — единичный `logger.warning` |
| Бизнес-аудит (кто создал заказ/лид/клиента, кто и когда менял статус заказа) | Да, но узко | `ActivityLog`/`OrderStatusHistory`/`TaskHistory` (модели, не `logging`-модуль) — только `CREATED`-события для Order/Task/Customer (`signals.py`) + история статусов заказа |
| Действия в Django admin (create/update/delete через `/admin/`) | Да, но не используется | Django встроенный `django.contrib.admin.models.LogEntry` — пишется автоматически для любой модели через admin, но нигде не выведен как отдельный «аудит-экран», нужно явно смотреть через `/admin/` |
| **Попытки логина (успех/неудача)** | **Нет** | Ни `logger`, ни модель этого не фиксирует — есть только throttle-отказ (429), но не запись «кто и когда не смог войти» |
| **Отказы в доступе (403/permission denied)** | **Нет** | DRF просто отдаёт 403, никакой записи не остаётся |
| **Чтение чувствительных данных** (кто открыл карточку клиента/заказ) | **Нет** | Ожидаемо для системы такого размера — полный read-audit почти никогда не нужен на MVP-стадии, но стоит знать, что его нет |

## 2. Куда уходят логи

Единственный handler — `logging.StreamHandler` в консоль (`settings.py: LOGGING`). На Railway это означает, что логи попадают в стандартный лог-вьюер платформы. **Не проверено:** срок хранения логов на стороне Railway, кто из людей имеет к ним доступ, есть ли экспорт/архивация. Нет внешней централизации (Sentry, Logtail, Datadog, ELK) — если Railway-логи чем-то ограничены по времени хранения, старые инциденты будет невозможно расследовать постфактум.

## 3. Утечка чувствительных данных в логи

Проверено: `grep` по `request.data`/`request.POST`/`password` в `api/v1/views.py` — нигде напрямую не логируется тело запроса или пароль. `_safe_error()` логирует само исключение и стектрейс, не сырые данные запроса — если исключение (например, `IntegrityError`) само по себе не включает значения полей в текст (обычно включает имена constraint'ов, не значения), утечки ПДн через эту точку не ожидается. Не проверялось построчно для 100% гарантии — стоит держать в уме при добавлении новых `except`-блоков.

## 4. Риски

| Риск | Приоритет |
|---|---|
| **Нет фиксации неудачных попыток логина.** Невозможно обнаружить брутфорс/подбор пароля постфактум — throttle его тормозит, но не оставляет следа для расследования (кто, когда, с какого IP пытался). Особенно важно в связке с находкой B2 (throttle слабее заявленного из-за `LocMemCache`). | **High** |
| **Нет фиксации отказов в доступе (403).** Если сотрудник (или скомпрометированный аккаунт) систематически пытается достучаться до чужих данных, это не оставляет следа для последующего разбора. | **Medium** |
| **Логи не централизованы, срок хранения не подтверждён.** При инциденте месячной давности логов может просто не быть. | **Medium** |
| **Django `admin.LogEntry` существует, но не используется как рабочий инструмент.** Дешёвый to leverage контроль, который уже есть «бесплатно» — просто никто на него не смотрит. | **Low** (это скорее упущенная возможность, не дыра) |

## 5. Рекомендации

1. **Залогировать неудачные попытки логина** — минимально: в `ThrottledTokenObtainPairView` (`auth_views.py`) добавить `logger.warning` при 401/400-ответе с username (не паролем!) и IP. Самый дешёвый и самый ценный пункт из этого раздела.
2. **Добавить `logger.warning` на 403 в кастомных permission-классах** (`api/permissions.py`) — хотя бы для чувствительных вьюсетов (Payment, Customer, Task), не обязательно повсеместно.
3. Уточнить у Railway срок хранения логов; если он короче, чем приемлемо для разбора инцидентов — либо настроить экспорт (даже простой webhook/файл), либо осознанно принять этот риск при текущем масштабе (1 клиент).
4. Не обязательно сейчас, но стоит иметь в виду при росте: outbox для security-событий (логин/логаут/смена роли/смена tenant membership) как отдельная лёгкая модель, а не полагаться только на `logging`-вывод в консоль.
