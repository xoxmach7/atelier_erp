# H1 — Resilience, Backup & Incident Response

Дата: 2026-07-20. Источники: весь репозиторий (`grep -rn "backup"` по `docs/*.md`/`README.md` — 0 совпадений, кроме этого чек-листа), memory `project_railway_deploy`.

**Главный вывод этого этапа: практически ничего не задокументировано и не проверено.** Это самый «слепой» раздел из всех десяти — не потому, что всё плохо, а потому, что backup/DR — единственная область, которую нельзя оценить чтением кода: она целиком определяется настройками Railway-аккаунта (план, включённые бэкапы), которые не видны из репозитория.

## 1. Что известно

| Вопрос | Ответ |
|---|---|
| Есть ли автоматические бэкапы Postgres? | **Не подтверждено.** Railway предлагает автоматические бэкапы на некоторых платных планах Postgres-аддона, но это включается в консоли Railway, не в коде — нет ни одного упоминания в репозитории, что это настроено или проверено. |
| Есть ли бэкап медиафайлов (R2)? | **Не подтверждено.** Cloudflare R2 поддерживает версионирование объектов, но не включается по умолчанию — не проверялось, включено ли для bucket'а этого проекта. |
| Есть ли задокументированная процедура restore? | **Нет.** Ни одного файла в `docs/` про восстановление из бэкапа. |
| RTO/RPO (сколько данных теряем / за сколько восстанавливаемся) | **Не определены.** Никогда не обсуждались и не тестировались. |
| Single points of failure | Один Postgres-инстанс, один backend-сервис (Railway), один R2-bucket — нет реплик, нет multi-region, нет staging-копии для проверки восстановления без риска для прод-данных. |

## 2. Риски

| Риск | Разбор | Приоритет |
|---|---|---|
| **Нет подтверждённой стратегии бэкапов БД.** | При потере/повреждении Postgres-инстанса (человеческая ошибка — например, неудачная миграция, `--reset` не туда; или сбой Railway) весь бизнес ателье (заказы, клиенты, деньги, история) может быть безвозвратно утерян. Учитывая, что `seed_demo --reset` уже разово выполнялся против прод-БД (2026-07-18, по решению владельца, с осторожностью) — процесс уже показал, что риск не гипотетический. | **High** |
| **Ни разу не тестировалось восстановление.** | Даже если бэкапы технически включены на стороне Railway, никто не проверял, что из них реально можно восстановиться за разумное время — бэкап, который никогда не восстанавливали, нельзя считать рабочим. | **High** |
| **Нет runbook на случай инцидента** (компрометация секрета, повреждение данных, недоступность сервиса). | Значит, при реальном инциденте решения будут приниматься в моменте, под давлением, без заранее продуманного порядка действий (что важнее — остановить утечку или сохранить улики; в каком порядке ротировать секреты, см. F1). | **Medium-High** |
| Single point of failure на каждом уровне (1 backend, 1 БД, 1 bucket) | Ожидаемо для пилотного масштаба (1 клиент) — не критично прямо сейчас, но стоит знать явно, а не полагаться на «Railway же managed, наверное справится». | **Low** на текущем масштабе, растёт с числом клиентов |

## 3. Рекомендации (без изменения кода — это организационная/конфигурационная работа)

1. **Прямо сейчас, до появления второго клиента:** зайти в Railway-консоль и подтвердить — включены ли автобэкапы Postgres, с какой частотой, где хранятся, сколько живут. Если не включены — включить (обычно это тумблер в настройках плана, не требует кода).
2. **Один раз протестировать полный цикл restore** на отдельном (даже временном) Railway-сервисе — не чтобы восстановить прод, а чтобы знать, что процедура реально работает и сколько времени занимает. Это и есть измерение реального RTO.
3. **Зафиксировать RPO осознанно** — например, «готовы потерять максимум 24 часа данных» — и убедиться, что частота бэкапов это обеспечивает.
4. **Короткий runbook на 1 страницу**: что делать при (а) подозрении на утечку секрета — порядок ротации из F1, (б) повреждении данных — откуда восстанавливаться, (в) недоступности Railway — есть ли план Б (скорее всего сейчас его нет и не нужен на этом масштабе, но стоит явно это признать, а не молчаливо предполагать).
5. Проверить, включено ли версионирование объектов в R2-bucket — защита от случайного/злонамеренного удаления фото/АВР.
