# C1 — Identity & Access Architecture

Дата: 2026-07-20. Источники: `roles.py`, `api/permissions.py`, `middleware.py`, `management/commands/seed_groups.py`, `seed_pilot.py`, `ensure_superuser.py`, модель `TenantMembership`, `SIMPLE_JWT` в `settings.py`.

## 1. Типы идентичностей

| Тип | Где заведён | Есть ли service accounts / API-ключи |
|---|---|---|
| Конечный пользователь ателье (5 ролей: Owner/Designer/Warehouse/Seamstress/Installer) | `auth.User` + Django `Group` (`roles.py` — единственный источник имён групп) | Нет разделения «человек vs бот» — все пользователи одного типа модели |
| Суперпользователь (`admin`) | `ensure_superuser` при каждом деплое, из `SUPERUSER_PASSWORD` | Один аккаунт на всю систему, приравнен к Owner везде через `user_in()` + `is_superuser` |
| Service accounts / API clients | **Отсутствуют.** Нет отдельных API-ключей, OAuth client credentials или m2m токенов — все обращения к API идут от имени человека через JWT, полученный логин/паролем. | Нет — если понадобится интеграция (веб-хук, внешний сервис), для неё сейчас нет отдельного механизма аутентификации, придётся заводить либо человеческий аккаунт под неё (плохая практика), либо строить с нуля. |

## 2. Аутентификация по каналам

| Канал | Механизм | Где хранится токен |
|---|---|---|
| Веб (Next.js) | JWT (access 60 мин / refresh 7 дней, ротация + blacklist) через `/api/auth/token/` | **Не определено в рамках этого аудита** — не проверялось, `localStorage` или что-то безопаснее (см. B2, перенесено сюда как открытый пункт — см. раздел 5) |
| Мобилка (Expo) | То же JWT | `expo-secure-store` (Keychain/Keystore) — закрыто 2026-07-11 |
| Django admin (`/admin/`) | Сессия Django (логин/пароль), отдельно от JWT-механизма | Django session cookie, `SESSION_COOKIE_SECURE=True` в проде |
| Browsable API DRF (`/api/auth/`) | `SessionAuthentication` (тот же логин/пароль, отдельная форма) | Тот же session cookie |

Три параллельных способа получить сессию/токен (JWT-логин, admin-логин, DRF browsable-логин) — все проверяют один и тот же пароль `auth.User`, так что это не три разных секрета, а один пароль с тремя точками входа. Увеличивает площадь атаки на брутфорс (см. B2 — throttle общий только на JWT-логине через `ScopedRateThrottle(scope='login')`; **admin-логин и DRF browsable-логин не имеют выделенного `login`-throttle**, у них применяется только общий `user`/`anon`).

## 3. Роли → права → данные

Матрица (см. `roles.py`, `CLAUDE.md`):

| Роль | Видит | Финансы | Полный список заказов |
|---|---|---|---|
| Owner | Всё | Да | Да |
| Designer | Все заказы, замеры, КП | Да | Да |
| Warehouse | Свой операционный срез (материалы) | Нет | Нет |
| Seamstress | Свой срез (пошив) | Нет | Нет |
| Installer | Свой срез (монтаж) | Нет | Нет |

Реализовано декларативно в одном месте (`ROLE_VISIBLE_STATUSES` в `role_scope.py`) и переиспользуется и для заказов, и для замеров — сильная сторона архитектуры (см. `project_role_scope_module` в memory), нет разъехавшихся копий правила.

## 4. Риски

| Риск | Разбор | Приоритет |
|---|---|---|
| **Скрытая избыточность прав у группы Owner в Django admin.** | `seed_groups.py`: `group.permissions.set(Permission.objects.all())` для группы Owner — это **все** Django model permissions (включая `auth.user`, `auth.group` — то есть теоретически управление другими аккаунтами через `/admin/`), не только бизнес-модели ателье. Сейчас не эксплуатируется, потому что ни у одного pilot-аккаунта с ролью Owner нет `is_staff=True` (`seed_pilot.py` не выставляет этот флаг) — доступ к `/admin/` фактически есть только у `ensure_superuser`-аккаунта. Но это **мина замедленного действия**: стоит один раз вручную выставить `is_staff=True` пользователю с ролью Owner (например, чтобы он мог зайти в admin посмотреть что-то) — и он получает полный CRUD по всем моделям в обход всего API-уровня RBAC/tenant-скоупа, который был так тщательно выстроен и не раз чинился. | **Medium-High** |
| **Нет MFA ни на одном канале.** | Только пароль — на JWT-логине, на admin, на browsable API. Для единственного superuser-аккаунта это означает, что утечка одного пароля = полный доступ ко всей системе целиком (все тенанты, все роли). | **High** (дублирует B2, тут — с точки зрения IAM-архитектуры, не только threat-инстанса) |
| **Admin-логин и DRF browsable-логин не имеют своего rate-limit.** | Throttle `scope='login'` привязан только к `ThrottledTokenObtainPairView` (JWT). У `/admin/login/` и `/api/auth/` (browsable) стоит общий `anon`/`user` throttle — тоже ограничение, но не специально заточенное под защиту от подбора пароля на конкретно этих формах. | **Medium** |
| **Нет разделения «человек vs интеграция».** | Если понадобится любая server-to-server интеграция (веб-хук от Cloudflare, будущий email-провайдер, будущий Sales CRM модуль из предыдущей задачи), для неё нет готового механизма (API-ключ с ограниченным скоупом) — есть риск, что кто-то заведёт для этого обычного `auth.User` с широкими правами «для простоты». | **Low** (пока нет интеграций — но стоит зафиксировать до того, как они появятся) |
| **`TenantMembership` — только ручное управление.** | Не риск, а факт архитектуры: назначение тенанта пользователю — только через management-команду/admin, нет самостоятельной регистрации. Уменьшает поверхность атаки (нет self-service onboarding, который можно было бы взломать), но требует ручной дисциплины при росте числа клиентов (см. P5 в CLAUDE.md — до сих пор не automated). | Инфо, не угроза |

## 6. Рекомендации к целевой IAM-архитектуре

1. **Не давать группе Owner `Permission.objects.all()` в `seed_groups.py`.** Owner и так получает полный доступ через кастомные permission-классы (`user_in(request.user, Roles.OWNER)`) — Django model permissions для admin-сайта ей не нужны, если только сам admin не планируется как рабочий инструмент Owner-роли. Если он не используется намеренно — сузить до `Permission.objects.none()` или конкретного набора.
2. **MFA хотя бы для `admin`/superuser-аккаунта** — самый простой шаг с наибольшим снижением риска (компрометация одного пароля сейчас = компрометация всей системы).
3. **Отдельный `throttle_scope` для admin-логина**, а не дефолтный `anon`.
4. **Если появится первая интеграция — заводить её через API-ключ с ограниченным скоупом**, а не через обычный `auth.User`-аккаунт; сейчас самое время зафиксировать это как принцип, пока прецедента ещё нет.
