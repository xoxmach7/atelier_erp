# Настройка автобэкапов БД (закрывает аудитный пункт #6)

Управляемый Postgres-плагин Railway **не имеет** готового тумблера «включить автобэкапы» в консоли — это не тарифная функция для plugin-типа Postgres, который использует этот проект (в отличие от отдельного продукта Railway Postgres с point-in-time recovery на более новых планах). Механизм пришлось собрать самостоятельно: `python manage.py backup_database` (`atelier_erp/management/commands/backup_database.py`) — делает `pg_dump -Fc` (custom format, восстанавливается через `pg_restore`, в отличие от `dumpdata`, который теряет часть структуры БД) и грузит файл в тот же R2-бакет, что и медиа, под префиксом `backups/`, с ротацией (по умолчанию хранит последние 14).

Код и тесты готовы и запушены. Дальше — **разовая ручная настройка в консоли Railway** (2 клика), потому что версия Railway CLI на момент этой задачи не даёт настроить ни custom start command, ни cron schedule для сервиса иначе, чем через дашборд.

## Почему это не сделано автоматически

Создание Railway-сервиса через CLI (`railway add --repo ... --service db-backup`) само по себе безопасно, но сразу после создания Railway начинает деплоить его с **дефолтной командой из Dockerfile** — то есть поднимет ещё один полноценный gunicorn-сервер поверх той же прод-БД, пока не задан отдельный start command и cron-расписание. Это стоило бы лишних денег и создавало бы дублирующий веб-сервис — поэтому сервис не создавался «вслепую».

## Шаги (один раз)

1. В Railway Dashboard → проект **Atelier_ERP** → **+ New** → **GitHub Repo** → тот же репозиторий (`xoxmach7/atelier_erp`), ветка `main`. Назвать сервис, например, `db-backup-cron`.
2. В настройках нового сервиса (**Settings → Deploy**):
   - **Custom Start Command**: `python manage.py backup_database`
   - **Cron Schedule**: `0 5 * * *` (раз в сутки, 05:00 UTC — можно любое другое время, вне пиковой нагрузки)
   - **Restart Policy**: `Never` (сервис должен просто отработать и выйти, не быть always-on)
3. В **Variables** нового сервиса — либо сослаться на переменные основного сервиса через `${{shared.VAR_NAME}}`/`${{Postgres.VAR_NAME}}` (Railway поддерживает ссылки между сервисами одного проекта), либо скопировать вручную:
   - `DATABASE_URL` — сослаться на переменную сервиса `Postgres` (внутренний адрес, `postgres.railway.internal` — публичный прокси заново поднимать не нужно)
   - `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_STORAGE_BUCKET_NAME`, `AWS_S3_ENDPOINT_URL`, `AWS_S3_REGION_NAME` — те же значения, что у основного сервиса `atelier_erp` (R2 для медиа)
4. Задеплоить. Первый прогон можно проверить руками — открыть логи сервиса, убедиться в строке `Бэкап загружен: s3://.../backups/...dump (... байт)`.
5. **Тест восстановления** (сделать один раз после первого успешного бэкапа, вручную): скачать файл из R2 (`.dump`), поднять временный локальный Postgres (Docker: `docker run --rm -e POSTGRES_PASSWORD=x -p 5433:5432 postgres:18`) и выполнить `pg_restore -h localhost -p 5433 -U postgres -d postgres --clean --if-exists /path/to/backup.dump`. Если восстановление проходит без ошибок — цепочка бэкап→восстановление подтверждена рабочей (это и есть требование аудита #6: «протестировать restore хотя бы раз»).

## Версия pg_dump

Postgres на Railway — **18.4** (проверено напрямую 2026-07-25 через временный TCP-прокси, сразу удалён после проверки). Dockerfile ставит `postgresql-client-18` из официального репозитория PGDG (в стандартных пакетах Debian bookworm пока нет клиента 18-й ветки) — это гарантирует полную совместимость `pg_dump` с сервером.

## Что не сделано намеренно

- Сам Railway-сервис `db-backup-cron` **не создан** — см. причину выше (риск поднять полноценный дублирующий веб-сервис вслепую, пока start command не настроен).
- Восстановление (шаг 5) не протестировано этим заходом — требует первого реального бэкапа в R2, которого ещё нет, пока сервис не создан.
