# F1 — Secrets Management Architecture

Дата: 2026-07-20. Источники: `settings.py`, `ensure_superuser.py`, `.env.example`, `.gitignore`, memory `project_railway_deploy`.

## 1. Инвентарь секретов

| Секрет | Назначение | Где задаётся |
|---|---|---|
| `DJANGO_SECRET_KEY` | Подпись сессий/CSRF, **и одновременно** подпись JWT (`SIMPLE_JWT['SIGNING_KEY'] = SECRET_KEY` — секрет переиспользован, не отдельный ключ) | Railway env var (backend) |
| `DB_PASSWORD` (+ `DB_USER`/`DB_HOST`/`DB_NAME`/`DB_PORT`) | Доступ к внутреннему Postgres | Railway env var (внутренняя сеть, `postgres.railway.internal`) |
| `DATABASE_PUBLIC_URL` | Публичный TCP-прокси к тому же Postgres (генерируется Railway автоматически при создании add-on) | Railway variables панель сервиса Postgres, используется вручную для one-off операций |
| `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` | Доступ к Cloudflare R2 (медиафайлы) | Railway env var (backend) |
| `SUPERUSER_PASSWORD` (+ `SUPERUSER_USERNAME`/`SUPERUSER_EMAIL`) | Пароль единственного superuser-аккаунта, применяется **на каждом старте контейнера** (`ensure_superuser` в `CMD` Dockerfile) | Railway env var (backend) |
| Пароли пилотных пользователей (`seed_pilot`) | Разовая генерация случайных паролей при сидировании | Генерируются в рантайме, выводятся в stdout команды — **не хранятся как секрет нигде отдельно**, ответственность за передачу пользователю и последующую смену — вне системы |

Секретов на фронтенде/мобилке нет — оба `NEXT_PUBLIC_API_BASE_URL`/`EXPO_PUBLIC_API_BASE_URL` являются публичными по своей природе (URL API, не секрет).

## 2. Хранение и загрузка

- Локально: `.env` (в `.gitignore`, не коммитится; `.env.example` — шаблон без реальных значений, чист).
- Прод: переменные окружения в панели Railway (backend) и, отдельно, Vercel (для фронтенда — но там секретов нет, см. выше).
- Никакого выделенного secret-manager (Vault, AWS Secrets Manager, Doppler) не используется — секреты живут ровно там, где их поддерживает сама платформа деплоя (Railway Variables). Для текущего масштаба (1 клиент, 2 сервиса) это нормальная практика, не архитектурный провал — but see §4 recommendations.

## 3. Ротация

| Секрет | Практика ротации |
|---|---|
| `DJANGO_SECRET_KEY` | **Нет документированной процедуры.** Смена этого ключа мгновенно инвалидирует все активные сессии и JWT (включая refresh-токены пользователей мобилки) — это должно быть осознанным действием с предупреждением пользователей, а не спонтанной сменой. |
| `SUPERUSER_PASSWORD` | Формально «ротируется» каждым деплоем (перечитывается из env), но фактически — только если саму переменную поменяли в Railway. Ручная смена пароля через `/admin/` откатывается следующим деплоем (см. B2/C1). |
| `DB_PASSWORD`, R2-ключи | Смена возможна через панели Railway/Cloudflare, но нет зафиксированной регулярности (по расписанию, после ухода сотрудника и т.д.) — процедура ad-hoc. |
| `DATABASE_PUBLIC_URL` | То же самое, что и `DB_PASSWORD` — они физически один и тот же пароль. |

## 4. Риски

| Риск | Приоритет |
|---|---|
| **`DJANGO_SECRET_KEY` одновременно подписывает Django-сессии и JWT.** Компрометация одного ключа даёт возможность подделать оба типа токенов. Стандартная практика — раздельные ключи (`SIMPLE_JWT['SIGNING_KEY']` можно задать отдельной переменной), сейчас переиспользуется `SECRET_KEY` за неимением явного решения. | **Medium** |
| **Нет процедуры и расписания ротации ни для одного секрета.** Дублирует F1-специфичную часть находки из B2/C1 (`SUPERUSER_PASSWORD`), но здесь — шире: то же верно для `DJANGO_SECRET_KEY`, R2-ключей, `DB_PASSWORD`. | **Medium-High** (совокупно, это системный пробел, не один секрет) |
| **Пароли пилотных пользователей проходят через stdout команды.** `seed_pilot` печатает пароли в консоль (Railway build/run logs) — если эти логи ретеншатся дольше, чем нужно, или доступны кому-то ещё, кроме владельца, это утечка учётных данных пользователей через лог, а не через код. | **Low-Medium** (масштаб сейчас маленький, 5 ролей на 1 ателье) |
| **Единая точка входа секретов = панель Railway/Vercel.** Кто из людей имеет доступ к этим панелям — не определяется кодом, это организационный вопрос (см. §5). | Не приоритизируется здесь — организационный, не технический |

## 5. Открытый вопрос (не решается из кода)

Кто именно имеет доступ к Railway/Vercel/Cloudflare консолям (сколько людей, есть ли общий логин или у каждого свой) — это чисто организационный факт, а не то, что можно вычитать из репозитория. Стоит зафиксировать отдельно, если в команде больше одного человека с доступом к секретам.

## 6. Рекомендации

1. **Разделить `DJANGO_SECRET_KEY` и JWT `SIGNING_KEY`** — задать `SIMPLE_JWT['SIGNING_KEY']` отдельной переменной окружения, чтобы компрометация одного не давала автоматически второй.
2. **Завести минимальный регламент ротации** — не обязательно сложный secret manager, достаточно чек-листа «что менять и в каком порядке при подозрении на утечку» (порядок важен: смена `DJANGO_SECRET_KEY` разлогинит всех, `DB_PASSWORD` требует синхронной смены и в Railway, и в приложении).
3. **`SUPERUSER_PASSWORD`-поведение при редеплое** — либо убрать автоматический сброс пароля из `CMD` (оставить `ensure_superuser` только для первого запуска/явного вызова), либо осознанно принять этот механизм и не пытаться менять пароль через UI (see C1/F1 — противоречие сейчас никак не зафиксировано, ловушка для будущего администратора).
4. Не критично сейчас, но при росте команды — рассмотреть secret-manager (даже встроенный Railway "shared variables" с ограничением по сервисам) вместо плоского списка переменных, доступных любому, у кого есть доступ к проекту целиком.
