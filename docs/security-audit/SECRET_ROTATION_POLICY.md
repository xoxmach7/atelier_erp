# Регламент ротации секретов

Закрывает пункт #11 из [J1-consolidated-overview.md](J1-consolidated-overview.md) — раньше не было расписания/процедуры ротации ни для одного секрета.

## Секреты системы

| Секрет | Где хранится | Что подписывает/защищает | Периодичность ротации |
|---|---|---|---|
| `DJANGO_SECRET_KEY` | Railway Variables (backend) | Django-сессии, CSRF-токены | Раз в 12 месяцев, либо немедленно при подозрении на утечку |
| `JWT_SIGNING_KEY` | Railway Variables (backend) | JWT access/refresh токены (см. `SIMPLE_JWT['SIGNING_KEY']` в `settings.py`) | Раз в 12 месяцев, либо немедленно при утечке. Если переменная не задана — используется `DJANGO_SECRET_KEY` (см. `settings.py`), рекомендуется задать отдельное значение при ближайшей плановой ротации |
| `DB_PASSWORD` | Railway Variables (backend + Postgres addon) | Доступ к базе данных | Раз в 12 месяцев, либо немедленно при утечке |
| Пароли сотрудников (`StaffManagementViewSet`/`AtelierManagementViewSet`) | Только хэш в БД, plaintext показывается один раз при создании | Вход конкретного сотрудника | По требованию сотрудника/владельца; принудительная ротация не автоматизирована |
| Пароль суперюзера (`admin`) | Railway Variables (`DJANGO_SUPERUSER_PASSWORD`, читается `ensure_superuser`) | Django admin, полный доступ | Раз в 6 месяцев (более короткий цикл — единственная точка входа с полным обходом RBAC) |

## Процедура ротации `DJANGO_SECRET_KEY` / `JWT_SIGNING_KEY`

1. Сгенерировать новое значение (`python -c "import secrets; print(secrets.token_urlsafe(50))"`).
2. Обновить переменную в Railway Variables.
3. Redeploy backend.
4. **Последствие ротации `DJANGO_SECRET_KEY`**: все активные сессии Django admin разлогиниваются (не критично — единственный superuser). CSRF-токены у открытых вкладок админки станут недействительны.
5. **Последствие ротации `JWT_SIGNING_KEY`**: все выданные JWT (access и refresh) мгновенно становятся невалидными — все пользователи (веб и мобилка) будут разлогинены и должны войти заново. Планировать ротацию JWT-ключа не как "тихую" операцию, а с предупреждением пилотного клиента о необходимости перелогиниться.

## Процедура ротации `DB_PASSWORD`

1. Сменить пароль в Railway Postgres addon (Railway обычно генерирует его сам — Regenerate Password в консоли).
2. Railway автоматически обновляет `DATABASE_URL`/связанные переменные для привязанных сервисов — подтвердить, что backend подхватил новое значение при следующем деплое.
3. Не забыть `DATABASE_PUBLIC_URL` (см. пункт #3 аудита) — это отдельная строка подключения, могла не обновиться автоматически.

## Триггеры внеплановой ротации (независимо от расписания)

- Секрет засветился в чате/скриншоте/публичном репозитории (см. [[feedback_secrets_handling]] в памяти сессий — уже случалось, пользователь предупреждён).
- Увольнение/смена доступа у человека, знавшего секрет.
- Любое подозрение на компрометацию сервера/аккаунта Railway.

## Не входит в этот регламент

- Пароли Fable/Vercel/GitHub-токенов — вне скоупа backend-секретов, отдельная организационная задача владельца.
- Автоматизация ротации (Vault, Railway API-скрипт) — не оправдана при команде из одного человека и одном клиенте; переоценить при росте.
