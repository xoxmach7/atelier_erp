# BUSINESS_FLOW_SCREENS.md

Экранная карта системы (UI) и матрица доступа по ролям.
Дополняет `BUSINESS RULES.md` (там — логика процесса и сущностей). Здесь — какие экраны существуют, что на них происходит и кто имеет доступ.

Источник: 16 скринов + описание бизнес-цепочки от владельца (зафиксировано 2026-06-03).

---

## Роли (уточнено владельцем 2026-06-03)

- **Владелец / Админ — ОДНО лицо** (одна роль). На скринах «владелец» и «админ» написаны как разные, но это один человек. КП — часть его процесса и процесса Дизайнера, не отдельная роль.
- **Замерщик / Дизайнер** — замеры, КП, клиенты, заказы.
- **Склад / снабжение** — только задачи по материалам.
- **Швейный цех** — только производственные задачи.
- **Монтажник / Установщик** — только монтаж и закрытие заказа, фотоотчёт.

### Срез доступа к заказам (явно)
- **Полный список всех заказов компании видят ТОЛЬКО 2 роли:** Владелец/Админ и Дизайнер.
- Склад — видит только **принятые** заказы (свой срез по материалам).
- Цех — видит только заказы **в производстве** (свой срез).
- Установщик — видит только **готовые / скоро готовые / просроченные** (свой срез).
- Принцип: каждый сотрудник видит только свои задачи и действия, а не весь список заказов.

### Маршрут (уточнён, порядок зафиксирован)
**Заказ → Замер → КП → Склад → Цех → Установка → Фотоотчёт.**
(То есть заказ создаётся первым, замер и КП — внутри заказа.)

### Оповещения
- Нужны оповещения о **горящих сроках** (дедлайн заказа близко/просрочен).
- Нужно оповещение от склада «надо закупить» (адресат — Владелец/Админ).

## Сквозная цепочка (как соединяются экраны)

1. **Вход** (1) → роль определяет доступ.
2. **Дизайнер/Админ**: создаёт клиента (6) → создаёт заказ (4) → снимает замеры (5, просмотр через 7).
3. Из всех замеров заказа (8) формируется **КП** → кнопка генерирует PDF. Клиент согласует КП.
4. После принятого КП заказ становится **принятым** → попадает на **склад** (9): склад проверяет обеспеченность (10), ищет у себя или инициирует закупку, передаёт в цех.
5. **Цех** (11–13): видит заказ в работе, размеры и изделия, шьёт, отмечает «пошили», меняет статус → заказ **Готов**.
6. **Установщик** (14): видит готовые / скоро готовые / просроченные → монтаж по карте навески (16) → **фотоотчёт** (15) → закрытие.

Главная статусная цепочка (из BUSINESS RULES):
**Новый → В работе → В производстве → Готов → На установке/выдаче → Ожидает финальной оплаты → Завершён** (+ Отменён).

## Открытые вопросы / нестыковки (требуют решения)

1. **Роль «Владелец»** не описана в `BUSINESS RULES.md`. Определить права: только сводка + просмотр, или полный доступ Админа.
2. **Кто видит список всех заказов (3)** — указаны Владелец и Дизайнер. Уточнить, видит ли Админ, и что видят Склад/Цех/Установщик (по описанию — только свой срез: принятые / в работе / готовые).
3. **«Пошивочный паспорт изделия»** (экран 11) — отмечено как будущая фича. Положить в бэклог.
4. **«Просрочен»** на экране установщика (14) — это контрольный сигнал/флаг, а не главный статус заказа (см. BUSINESS RULES). На UI показывать как метку, не как стадию.
5. **Передача «склад → цех»** (9) — нужен явный триггер/действие, фиксирующее переход обеспечения в пошив.
